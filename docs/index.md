# 量潮数据产品定位

## 一句话定位

> **帮客户看清自己的数据，也看清数据是怎么被处理的。**

## 核心矛盾

量潮数据的客户不是数据分析师，而是业务方——运营、销售、管理者。他们：

- **说不清需求**：脑子里是业务问题，不知道翻译成什么数据规格
- **看不懂过程**：中间结果发过去，不知道"这是处理前还是处理后"
- **信不过结果**：最终交付物拿到了，不知道"这是不是我当初要的那个"

这不是项目管理问题，是**沟通翻译问题**。产品的核心不是帮内部团队管项目，而是帮客户从"模糊的业务感觉"走到"确认的数据交付"。

## 产品形态：引导式数据服务

传统的项目协作工具把流程管给内部团队看；量潮数据反过来，把流程呈现给客户理解和确认。

| 阶段 | 客户需要什么 | 产品做什么 |
|------|-------------|-----------|
| 1. 表达需求 | 客户说不清"帮我分析数据"之外的细节 | 用场景模板引导客户一步步勾选：数据源、时间范围、对比维度 |
| 2. 理解方案 | 客户看不懂"ETL清洗流程" | 把处理步骤翻译成可视化故事线：原始数据长这样 → 去重后变这样 → 合并后变这样 |
| 3. 确认进度 | 客户想知道"做到哪一步了，我看看" | 每个处理节点都可预览中间结果，客户确认后再进入下一步 |
| 4. 验收交付 | 客户需要验证"这是不是我想要的" | 交互式报告，可筛选、下钻、回溯历史版本 |

## 与 qtclass 的关系

两者共享同一个引导引擎的内核：

```
引导引擎
├── 把复杂过程拆成用户可理解的 Scene（场景）
├── 每步：展示信息 → 用户选择/确认 → 进入下一 Scene
├── 选择影响分支路径
└── 最终完成"从模糊到确认"的转化
```

| | qtclass（教学） | qtdata（数据服务） |
|---|---|---|
| 用户 | 学员 | 客户（业务方） |
| 困境 | 不懂某个知识点 | 说不清数据需求、看不懂处理过程 |
| 场景输出 | 教学视频 + 分支练习 | 数据预览 + 处理步骤可视化 |
| 确认节点 | 课后测验 | 需求确认、中间结果确认、验收确认 |
| 最终产出 | 学员获得知识 | 客户获得数据产物 |

## 当前能力

落地在现有代码中的形态：

- **看板**：需求探索 → 约定启动 → 执行监控 → 验收交付，展示项目全过程
- **Pipeline 视图**：数据处理流水线可视化，每个节点对应数据处理步骤和数据集
- **Demo 数据**：工厂产量数据分析（导入 → 清洗 → 合并 → 计算 KPI → 生成报告），体现了"让客户看到数据在每个阶段长什么样"的思路

## 演进方向

1. **看板列 → Scene**：用引导式界面替代静态列，每步引导客户确认
2. **Pipeline 节点 → 可预览的中间成果**：不只是展示"做了去重"，而是展示"去重前 500 行 → 去重后 480 行，这 20 行删掉了"
3. **需求表达 → 场景模板引导**：从空白需求表单变成"你的场景是哪种？→ 销量分析 → 选时间范围 → 选对比维度 → 自动生成需求初稿"
