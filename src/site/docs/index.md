# 量潮数据官网介绍页面设计

本文明确量潮数据官网介绍页（`src/site` 首页）的定位、区块结构、内容来源、文案约束与验收标准，作为首页改版的实现依据。部署链路与域名不在本文范围，见 `src/site/ROADMAP.md`。

## 页面定位

页面服务的对象是从知乎、小红书、公众号等渠道初次到访的潜在客户，主要是高校经管科研工作者与高新科技企业，也包括个人数据需求方。这类访客了解量潮的背景信息少、判断时间短，页面需要在一次浏览内回答三个问题：我们做什么、你的需求是否匹配、如何开始。

页面只有一个转化目标：访客发邮件至 data@quanttide.com 描述需求，我们在 1 个工作日内回复。所有区块为这一个目标服务，不设并列入口。

现状首页仅三段静态文案——业务定位、服务对象、核心竞争力，缺少流程、交付物、案例与联系方式，访客无法完成上述三个判断。本设计在现有 section 与卡片结构上扩展，不推翻既有组件形态，同时对现状文案作两处调整：

- 首屏导语不再沿用「卡在需求大而市场供给稀缺的位置上」。该句依赖内部语境，初访者无法解码，改用宣传册的核心命题：把原始数据变成可靠、可用的结构化数据
- 「核心竞争力」区块撤销。数据工程能力由服务规模的公开数字承载，产教融合改写为页脚一句沿革（核心团队在浙江理工大学计算机系承担专业课教学），原卡片中涉及内部培训分工的表述不对外出现

## 区块结构

页面自上而下由八个区块组成。

### 1 首屏

呈现品牌名、一句话定位与主行动按钮。标题「量潮数据」与副题「数据处理服务与咨询」沿用现状。导语为核心命题句。主按钮「描述你的需求」以 mailto 链接指向 data@quanttide.com。

### 2 我们为谁服务

两类客户各一张卡片。科研团队：将原始数据加工为可直接用于论文分析的数据集，交付附带处理日志，论文评审时可溯源。企业研发团队：从大规模非结构化数据中提取结构化信息，用于知识库或模型训练。区块结尾一句话说明两类需求的共同核心挑战，并注明可签署保密协议。

### 3 服务规模

用公开数据建立可信度：已服务多所高校课题组与企业；数据条目平均在 100 万以上、最大数十亿；数据量平均在 50 GB 以上、最大 10 TB；项目周期一般一周到三个月。数字口径以宣传册为准，实现时不得改写或四舍五入。

### 4 合作流程

呈现「你会经历什么」五步：需求沟通、方案确认、执行与同步、交付与验收、后续支持，每步一句说明当步产出。强调过程可见：进度报告、处理日志与中间结果在执行期随时可查。对外只呈现此简化五步，内部用户故事地图中的完整权责划分不进入本页。

### 5 交付物

三样核心交付，各配一句说明。数据蓝图：设计阶段交付，描述从原始到目标状态的处理方案与链路设计。数据集：实施阶段交付，附数据字典与字段说明。数据报告：交付阶段交付，记录每步处理逻辑、参数与中间结果，可复现、可审计。附归属说明：数据集归客户，数据蓝图与数据报告知识产权双方共有。完整交付清单（数据处理器、数据应用、项目管理文档、商务报价单）留给服务详情页，不进入本页。

### 6 项目案例

以制衣厂数据清洗案例作为信任建立的主体：高校研究者拿到工厂数据无法直接使用，我们完成问卷、工序、产量三个模块的清洗与对齐，按期交付。引用客户原话作为社会证明，配完整复盘文章外链（URL 由运营补充）。案例卡下方列出同类场景：电商评论文本挖掘、GitHub 开发者行为数据采集清洗、金融财报文本提取，向访客示意需求的普遍形态。

### 7 常见问题

收录四个高频问题，一问一答各两句以内：适合的项目规模、交付周期、计价方式、数据安全。计价只说明分阶段制定报价与付款周期的机制，不公开具体价格；数据安全说明可签署保密协议。

### 8 页脚

联系邮箱 data@quanttide.com 与回复时效，投诉邮箱 we@quanttide.com，沿革一句话（2016 年以课题组形式承接数据项目，2018 年成立量潮科技；核心团队在浙江理工大学计算机系承担专业课教学），以及公司主体与版权信息。邮箱一律为可点击的 mailto 链接。

## 内容来源

每个区块的文案必须可追溯到档案库既有材料，不独立创作业务表述。

- 首屏、我们为谁服务、服务规模、合作流程、交付物、常见问题：`data/brochure/qtdata/who.md`
- 项目案例：`data/brochure/qtdata/when.md`
- 后续服务详情页：`data/brochure/qtdata/index.md` 与 `data/brochure/qtdata/what.md`

## 文案基调

- 全文书面语，每句脱离上下文可独立成立，不预设读者了解量潮的内部概念
- 不使用内部管理用语，如「可替代」「议价权」「稀缺环节」；能力表述落在「项目经验沉淀为工程规范」，不落在个人分工
- 数字、承诺、交付条款只用宣传册口径，不出现宣传册之外的量化承诺
- 不出现内部战略与平台规划，如云体系、路线图、内部系统名称
- 中文引号，不用连续形容词堆叠与空泛赞誉，如「行业领先」「顶尖」一类词不使用

## 实现约定

- 沿用现有 section 加卡片的结构与 `App.css` 样式体系；区块内容以结构化数组定义，现状 `App.tsx` 的 `audiences`、`strengths` 已是此形态。按 ROADMAP v0.2.0「首页内容契约化」，后续将文案迁出为本地 JSON 契约，组件只负责渲染
- 文案单一事实源：官网文案与宣传册出现分歧时以宣传册为准，修改时两处同步
- 外链仅案例复盘文章一处，新窗口打开

## 验收标准

1. 首屏在五秒内可判断业务内容与联系动作
2. 每一区块文案可追溯至内容来源所列文件，无来源之外的业务表述
3. 全页仅一个转化目标，联系入口只出现在首屏主按钮与页脚
4. `npm run build` 构建通过，无死链，邮箱与外链可点击
5. 陌生访客复述测试：浏览后能准确说出业务内容、合作方式与联系途径
